# Contributing to Split

Welcome to Team Split!

This markdown document describes how our team plan to work together on Split. The practices below should be reviewed by the team before begin contributing and followed as works are being done. 

This guide may be updated as the project develops. 

## Team Norms

- Communicate respectfully.
- Raise and escalate blockers early on.
- Keep the project board up to date.
- Check in with team before taking over work; avoid redundant work.
- Always ask for help when needed!
- There are no "stupid" questions. 
- Share enough context when communicating. 
- Record contributions accurately. 
- Follow up, follow through, close the loop. 

## Sprint Planning and Stand-ups

At sprint planning, we: 
- ... review the priorities
- ... choose user stories
- ... break larger tasks into smaller tasks and spikes. 
- ... estimate user stories with Planning Poker, using physical cards held up on camera (story points 1, 2, 3, 5, 8, 13, ?). With a standard deck: A=1, 2, 3, 5, 8, K=13, Joker=?.

Each sprint lasts about 2 weeks and follows the course schedule. The Scrum Master and Product Owner roles rotate every sprint, so every member holds each role at least once. The current holders are listed in the README.

Stand-ups are held on Tuesday, Friday, and Sunday at 8:00 PM ET in the team's Discord voice channel and last at most 15 minutes. Everyone attends live. After each stand-up, every member's answers are posted in the team's Discord stand-up thread.

Each member shares:
- DID:      What they have completed since the previous stand-up.
- DOING:    What they plan to work on next.
- BLOCKERS: Any hurdles or help they need.

## Git Workflow

- Create a branch from the latest master in the team repository.
- Keep commits focused with single-line messages. 
- Push progress between stand-ups.
- Never commit directly to master.
- Open a pull request to the team's master branch. GitHub defaults the base repository to the instructor's repository, so change it to ours. Include the related issue and checks performed.
- Never approve your own pull request.
- Review with the team before merging, then update the board.

## Contributions

- Contributions include:
    - Code
    - Design 
    - Documentation 
    - Tests 
    - Research. 
- Check the board before starting and discuss scope changes with the team.
- Follow the existing code style and convention
- Cite all sources.
- Never commit secrets.
- Work is considered done when: 
    - Requirements are met 
    - Checks and review are complete
    - Result is merged
    - Changes are documented.
- Comply with all course policies. 

## Local Development

- See [README.md](README.md#running-the-front-end) for how to set up, run, build, and lint the front-end.
- The back-end folder only contains a placeholder file for now.
- Keep secrets in a local .env file. Do not commit it.

## Handling Disagreements

- Discuss disagreements directly with the team.
- Ask the Scrum Master for help with coordination, or the Product Owner to clarify product priorities.
- If the issue remains unresolved, ask the instructor for guidance.
